核实过的现状

  • public/ 目录下只有 icons/，没有 manifest.json，没有 sw.js——这个 app 现在连"可安装到主屏幕"这层 PWA 基础都没有，更别说离线缓存。
  • App Router 的每个页面都是 Server Component，数据在服务端渲染时查一次 D1，断网时这次请求直接失败，浏览器展示的是它自己的失败页（不是这个 app 设计的任何界面）。
  • 参照项目里另外两个真的做过离线支持的项目——remy-calc/remy-gold——CLAUDE.md 记录的教训是"离线 SW 一旦引入就有 iOS 白屏风险，必须走版本同号 + node --check + SW 导航回归测试 + 部署回读四道关卡"，这个项目做离线也要照抄同一套四道关卡，不能只是随手加个 sw.js 就上线。

怎么做（技术方案）

  • SW 缓存策略：新建 public/sw.js，只缓存"读"这类 GET 请求的最近一次成功响应（行程详情、活动流、结算、支付方式列表这几个页面各自的数据），不缓存写操作（POST/PATCH/DELETE 断网时应该直接失败或进第二期的队列，不是"假装成功"）。跟 remy-calc/remy-gold 同一套"去重定向"处理逻辑，避免 iOS Safari 那个"Response served by service worker has redirections"白屏坑。
  • 数据快照存哪：用 IndexedDB（不是 localStorage，数据量可能超过 localStorage 单个 key 的大小上限，尤其记账笔数多的长行程）存最近一次成功拉到的行程详情+活动流+结算+汇率缓存，每次联网成功查询后原样落一份快照，不用额外的同步逻辑。
  • 顶部标示：用 navigator.onLine + online/offline 事件监听判断网络状态，离线时在页面顶部（`TripHeaderNav` 下面）插一条深色横条"📴 离线 · 数据截至 HH:MM"，时间取快照落地时的时间戳，不是"现在"——让用户清楚知道自己看到的是旧数据，不是实时的。
  • 离线时的写操作：这一期不做记账队列（那是第二期），离线时点"记一笔消费"依然可以打开表单填写，但提交按钮点击后如果侵测到 !navigator.onLine，直接提示"现在离线，这笔账先记在心里，恢复网络后再补记"，不假装能提交成功，避免用户以为记上了、联网后却发现没有这笔账。
需要 Remy 确认：离线时汇率比价卡怎么处理——这一期"离线记账"本身不支持提交，但比价卡这种纯查询功能理论上可以离线继续用缓存汇率算（不需要写操作），要不要在第一期就把汇率缓存也纳入离线快照范围（多一点工作量，但比价卡断网也能用体验更完整）？还是这个功能第一期先不管，断网时比价卡直接隐藏/提示"需要联网"？

怎么做（技术方案）

  • 队列存哪：同样用 IndexedDB 开一张本地"待同步"表，离线记账表单提交时不打真实的 POST /api/trips/{tripId}/expenses，先落一条本地队列记录（带临时本地 ID），活动流里这笔用 ⏳ 待同步 徽章标出来，视觉上跟其它正常消费混在一起（按时间排序），不是单独挪到别的地方。
  • 自动同步：online 事件触发时，队列里的记录按创建时间顺序依次真正提交给后端，成功一条就从队列里摘掉、换成正常消费（后端返回的真实 ID 替换本地临时 ID），提交中显示 🔄 同步中，失败显示 ⚠️ 同步失败，点击重试。
  • 汇率怎么处理：离线记非本位币消费需要填汇率，这时候拉不到实时中间价——用第一期已经缓存的最近一次汇率快照（GET /api/trips/{tripId}/fx-mid-rates 的最后一次成功响应）当默认值，跟现在"汇率自动带入"逻辑的 liveMidRates 是同一个变量，只是数据来源从"这次请求"变成"上次缓存"，用户依然可以手动改。
  • 冲突处理：这个 app 的"编辑/删除消费"目前是"最后写入者生效"，没有版本号或者乐观锁。离线队列引入之后可能出现的冲突场景：①这笔消费被同行人（如果他也有账号+离线权限，目前访客同行人大概率不具备完整离线能力，这条更多是给 Remy 自己多设备场景考虑）在线上先改了或删了，本地队列还在等着提交一笔基于旧数据算的分摊；②同一个钱包在离线期间被多笔消费扣款，恢复联网批量提交时钱包余额需要按提交顺序依次重算，不能并发写导致覆盖。方案：队列严格按时间顺序依次提交（不并发），每笔提交前用后端最新数据重新校验一次分摊/余额（复用现有 POST 逻辑本来就会做的校验），如果发现依赖的数据（比如这个支付方式已经被删除）已经不存在，这笔标记"⚠️ 同步失败，需要你确认"，弹一个简单提示让 Remy 自己决定要不要改成别的支付方式重新提交，不做静默丢弃或者静默覆盖。
风险提示：队列+自动同步+冲突处理这一整套比第一期复杂得多，涉及"本地临时 ID 换真实 ID"、"多笔消费依赖同一个钱包时的顺序重算"这类需要仔细设计的状态机，建议第二期正式排期前先单独过一次更细的技术方案评审（不只是这份产品向的对照稿），别急着直接写代码。

为什么第一期先做

理由：第一期（SW+快照+离线标示）是纯读取路径，风险集中在"缓存策略对不对、iOS 白屏坑有没有踩上"这一类已经在 remy-calc/remy-gold 两个项目上验证过标准解法的技术问题，工作量和风险都可控，而且立刻就能解决 Remy 最常遇到的场景——出差时信号不好，至少能看到上次同步的账，不用对着一片空白/错误页。第二期（离线记账队列+冲突处理）涉及本地临时 ID 换真实 ID、多笔依赖同一钱包的顺序重算、失败后人工确认这几个需要更谨慎设计的状态机，如果两期一起做，第二期的复杂度会拖慢第一期本该很快就能交付的价值。

风险：第一期主要风险是 SW 缓存策略写错导致"看到的永远是旧数据、联网了也不自动刷新"（这个项目里 reference_local_playwright_test_hits_stale_sw_cache 这条历史教训提到过测试环境下类似的坑，实现时要注意联网后主动重新拉取校验），照抄 remy-calc/remy-gold 部署脚本那套版本同号+SW 导航回归测试可以把这个风险压到很低。第二期主要风险是冲突处理设计不完整导致"离线记的账丢了/记错了"，比"没有离线功能"更糟——这条已经在上面一屏的风险提示里单独标出来，建议第二期正式动工前多一轮技术方案评审。
