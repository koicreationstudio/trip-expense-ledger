改了什么

没有 service worker，没有任何离线缓存——断网时所有 fetch 请求直接失败，Next.js 的 server component 数据请求拿不到任何东西，页面渲染失败或者卡在浏览器原生的"无法连接"提示
加 SW（public/sw.js），首次成功加载任何一趟行程主页/活动流/结算页时，把渲染用到的关键数据（消费列表/钱包余额/汇率缓存）写进一份本地快照（localStorage 或 IndexedDB，具体选哪个见下面④的判断），断网时页面从这份快照渲染，不再依赖网络请求

为什么不是"离线也能操作全部功能"，只是"离线也能看"

这个 app 现在几乎每个数据请求都要么读 D1（server component 直接查库），要么走 API route（client fetch）——两者断网都会失败。真正做到"离线也能看"，最小可行的做法是给几个最常看的只读页面（行程主页/活动流/结算页）各自存一份"最后成功渲染时的数据快照"，断网时检测到 navigator.onLine === false 或者 fetch 失败，就退回渲染这份快照，不是要把整个 app 的每个 server component 都改成离线可用（那个工程量大得多，也不是 Remy 这次提的诉求——她提的是"离线能看"，不是"离线能做所有事"）。

怎么做

离线提交表单时，先把这笔消费的完整表单数据（跟正常提交给后端一样的 payload）存进一个本地"待同步队列"（IndexedDB，理由见④），同时立刻在本地内存/UI 状态里插入一条"乐观渲染"的记录（跟这个项目已有的拖拽排序 dragOrderOverride 那种"乐观更新，等服务端确认再收敛"的模式是同一个思路，不是新发明一套状态管理），前面挂一个「⏳ 待同步」小标签。金额/分类/参与者选择跟在线时完全一样，不因为离线而阉割功能——差别只在"提交"这一步是存进本地队列还是直接打 API。

离线时汇率怎么办

Remy 原话"离线汇率用缓存"——记账表单需要自动带入汇率的场景（第一期任务①已经改好的"当地金额双向联动"那个功能），离线时改成读本地缓存的最近一次汇率（/api/trips/{tripId}/fx-mid-rates 这个接口第一期①的双向联动逻辑已经在用它，缓存下来的值离线时复用），不強制用户必须联网才能记账，缓存汇率可能不是当天最新，跟顶部离线状态条一样给个"缓存汇率，可能不是今天的"这类提示。

存哪、怎么判断冲突

本地待同步队列用 IndexedDB，不是 localStorage——待同步的记账表单数据结构化程度高（金额/分类/分摊明细/收据文件都可能有），localStorage 只能存字符串、有 5MB 上限，收据附件（如果离线也想拍照先存起来）更是塞不进去；IndexedDB 原生支持结构化数据+更大容量+能配合 SW 的 background sync，是这类"离线队列"场景的标准选择，不是过度设计。

冲突判定：这个 app 目前没有版本号/乐观锁字段（expense 表没有 version 这类列），这次离线同步最简单可靠的冲突判定是"如果这笔账依赖的父资源（这趟行程/这个钱包）在离线期间被别人删除或者这个人自己的账号在别处被登出，上传时后端会用现有的 404/401 校验自然拒绝"——不新增一套复杂的版本号机制，只处理"上传时目标资源还合法存在"这一种冲突场景；真正"两台设备同时改同一笔消费"这种细粒度冲突，这次不做（这个 app 目前多设备协作本来就没有做这层保护，是个更大的既有缺口，不是离线功能这次要补的）。

上传失败怎么办

队列里这一条标"⚠ 同步失败"，点击可以看到失败原因（比如"这趟行程已经被删除"），提供"重试"或"放弃这笔（删除本地待同步记录）"两个选项，不自动静默丢弃，也不无限重试卡住整个队列（这一条失败不阻塞队列里其它条目继续上传）。

⑤ 分期实施计划

总体计划
第一期离线能看（SW + 数据快照 + 顶部状态条）

理由：纯只读，不涉及任何写入/冲突/队列逻辑，风险最低、落地最快，能立刻解决"断网直接白屏"这个最基础的可用性问题，是"离线记账"这个更复杂功能的地基（第二期的队列也要靠 SW 拦截请求）。风险：SW 缓存策略如果写错，历史上 remy-calc/remy-gold 都踩过"SW 把旧版本 HTML/JS 缓存住，发新版之后用户还在用旧代码"的坑（remy-calc 2026-06-18 那次"裸推 SW 改挂 iOS 白屏"事故），这次必须照抄那两个项目已经验证过的 deploy.sh 五道关卡套路（版本号同步/node --check/SW 导航回归测试/部署后回读），不能简化。

第二期离线记账待同步队列

理由：涉及本地队列存储、乐观渲染、恢复网络后的自动上传、失败/冲突处理，工程量和风险都明显高于第一期，且依赖第一期的 SW 基础设施先落地稳定。风险：这个 app 目前没有为多设备/多次编辑设计任何版本控制机制，离线队列本质上是在一个"本来就没有强并发保护"的系统上加一层"延迟提交"，如果 Remy 使用场景里经常两台设备同时离线记账同一趟行程，冲突处理这块可能需要比这次稿子设计的更完整，这次先按"单设备离线记账为主"这个假设设计，如果实际用起来发现冲突频繁，需要回头补强。

需要 Remy 确认：①认不认可"先做第一期离线能看，第二期离线记账另外排期"这个顺序（不是一次性两期一起做）？②第一期的离线快照要覆盖哪几个页面——这份稿子先假设是"行程主页+活动流+结算页"这三个她最常看的页面，其它页面（支付方式设置/邀请管理等）离线时维持现状（显示网络错误），这个范围是否同意？
