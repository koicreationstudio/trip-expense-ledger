改了什么

「我持有」是一个单选下拉（MYR／USD／HKD／CNY 等 8 个候选），选中哪个币种，就只显示「结算币种＝＝这个币种」的那几张卡（fx-compare-card.tsx 第 591-597 行 cardRows = ... .filter(r => r.settlementCurrency === effectiveHold)）——这是一个「货币换算器」的框架：先选好你手上拿的是哪种钱，再看能换成什么。
整个「我的支付方式」这一块换成「这笔要付多少当地钱」的框架：不用先选"我持有什么"，直接列出全部 6 个已启用的支付方式各自要花多少钱，不管它们的结算币种是不是跟本位币一样。

根因读代码确认——正确的算法早就写好了，只是没接对地方

lib/domain/fx-recommendation.ts 的 recommendPaymentMethods() 这个纯函数，输入就是「一笔当地金额＋原始币种＋比较币种＋全部支付方式列表」，对每个支付方式各自算出 costInCompareCurrency（换算成比较币种后的等值成本，已经把加点/手续费/固定费/现金回赠都算进去了），排好序返回——这正是 Remy 想要的"以要付的当地金额为准，比较每个支付方式各自要花多少"。这个函数本身没有 bug，问题是行程主页这张"汇率比价"卡片（fx-compare-card.tsx）从来没这么用过它，而是在这层外面包了一个"先选我持有的币种"当筛选闸门，把这个函数的能力浪费了。旁边还有一个 FxCompareList 组件（app/trips/[tripId]/fx-compare-list.tsx），本来就是照这个函数的排序结果渲染列表用的，round4 时从记账表单搬走"搁置"，现在完全没有任何地方引用——这次改版就是把这两块现成的东西接回行程主页，不是要新写一套排序/换算逻辑。

判断"并列"的口径

不是比较浮点数是否完全相等（浮点数比较相等本身就容易出岔子），是四舍五入到显示用的最小货币单位（分）之后是否相等——costInCompareCurrency 本来就是整数分，天然不会有浮点误差，直接比较排序后最前面几行的 costInCompareCurrency 值是否跟第一行相等，相等的全部归入"并列最划算"这一组。

"比第二便宜的省 X%"这句话什么时候才出现

只有当"并列最划算"这组之外还有别的方式、且价差不是 0 时才显示这句话，价差用 (第二组成本 - 最划算成本) / 最划算成本 算百分比，同时给一个约等值的钱数（"约 HK$50"），不是只给一个孤零零的百分比——大金额时 1% 看起来很小，但配上"约 HK$50"这个具体数字，才好判断值不值得为了省这点钱专门换一张卡。

更细一档：差距很小但不完全是 0 时怎么说（避免"多换 0.0%"式的尴尬重演）

差距徽章结论行/单行文案
差距 = 0（四舍五入到分之后完全相等）每个并列的行都打「并列最划算」"最划算：A / B / C，三个打平，都是 HK$212.00"——列出全部并列的名字，不说"多换 X%"
0 < 差距 < HK$0.5 或 < 0.1%（四舍五入后显示会是 0.0% 但实际不为零）只给排第一的打「✓最划算」不显示百分比这句比较（避免"0.0%"这种精度不够又硬要显示的尴尬），改成"最划算：A，比 B 差距不到 HK$0.5，基本没差"
差距 ≥ HK$0.5 且 ≥ 0.1%只给排第一的打「✓最划算」正常显示"最划算：A，比 B 多花 HK$X.XX（Y.Y%）"
需要 Remy 确认："打平"的判定阈值——上面②③屏用的是"四舍五入到分之后完全相等才算打平"这个严格口径，这一档补充规则是"差距 0～0.5 分/0.1% 之间不算打平，但也不硬显示看起来很怪的 0.0%"。要不要把"打平"本身的判定也放宽到"差距 < 5 分也算打平"（现金换算本来就有取整误差，差 1～2 分可能只是舍入噪音，不是真的有优劣）？这版先按"分毫不差才算打平"的严格口径画，确认后再看要不要放宽。
