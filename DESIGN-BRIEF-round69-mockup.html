需要动到的后端逻辑（这轮只画不改代码，先标注清楚，免得实现时漏掉）

改了什么

const showCards = hasPaymentMethods && effectiveHold === baseCurrency;（fx-compare-card.tsx 第 353 行）
const showCards = hasPaymentMethods; —— 资格判断只看"有没有配置过支付方式"，不再叠加"我持有是不是等于本位币"这条

这句提示整段删除；每行「我的支付方式」旁新增一个结算币种徽章（class="settle-badge"，bg-cream #F3E9D2 / 深字 #7a5f13text-[8px] font-semibold px-[5px] py-[1px] rounded-full），标"结算 MYR"/"结算 HKD"，让用户自己看得出这张卡是不是跟"我持有"同一个币种，不靠隐藏来避免"精度不一样"的疑虑，靠透明标注

为什么原规则不只是"审美判断"，推翻它牵涉真实的计算逻辑（这条必须如实说清楚）

读了 /api/trips/{'{'}tripId{'}'}/fx-recommendation/route.ts 第 65 行：compareCurrency: trip.baseCurrency——这个值写死是行程本位币，从来不是"我持有"选的币种。而 fx-compare-card.tsx 第 573 行算"我的支付方式"这一行的隐含汇率：impliedRate = notionalTargetAmountYuan / costYuan，这个公式只有在 compareCurrency === effectiveHold 时数学上才是对的（分子是目标币种金额，分母必须是"持有币种"的成本，才能算出"1 持有币种=?目标币种"）。原规则把 showCards 锁死在"持有=本位币"，恰好让这两者永远相等，这不只是"怕精度不一样"的主观判断，是在保护一个真实存在的公式前提。

结论：单独放开 showCards 这一行不够，还要把 fx-recommendation 路由的 compareCurrency 参数从写死的 trip.baseCurrency，改成前端传来的 effectiveHold（"我持有"当前选中的币种），后端每张卡的成本才会真的按"我持有"这个基准算，不是继续用本位币算出来的数字硬凑一个"看起来对"的比率。这版截图上的数字（HSBC 1.9035 / Maybank 1.9227）是按"如果 compareCurrency 改成 MYR"重新手算的示意值，不是从生产环境截的——生产环境现在还没做这个改动，数字会不一样。

现有 schema 调查结论

查了 lib/db/schema.ts（第 500-531 行），项目里已经有一张几乎同形的先例表 fx_compare_preference（2026-09-24 刚建，同样是"按 user_id/participant_id × trip_id 存一份 JSON 偏好，两个 partial-unique index 分流有账号/访客两条轨道"这套模式）——这不是要凭空设计一套新机制，是有现成范本可以照抄。

建议：新建一张同形的表（比如 activity_list_preference：sortMode text + filterState json + updatedAt），不建议直接在 fx_compare_preference 里加字段——两个功能语义不同（一个是汇率比价的选项，一个是消费列表的排序筛选），混进同一张表会让它变成"两个不相关功能的字段大杂烩"，以后谁改其中一个功能的字段容易误伤另一个。分开建表、复用同一套 owner 双轨模式，风险更低也更好读。fx-compare-preference/route.ts 的 GET/PUT 结构（owner filter + onConflictDoUpdate + userId/participantId 双轨判断）可以直接照抄。

零写测试要求（这条是这次设计的硬指标）

只有用户真的手动改了排序或筛选，才允许发 PUT；页面加载、从本机缓存恢复显示，绝对不能触发任何写请求。

更正一个跟派工描述不一致的地方（如实核对代码后发现）：派工描述里说 fx-compare-card"打开页面就把 updated_at 原样 PUT 一次，从来没修过"——查了 fx-compare-card.tsx 源码和 fx-compare-card.test.tsx，这个坑实际上已经在 round66 修过，专门有一份测试锁死（describe('FxCompareCard — round66 零交互不写 D1')）。round66 的修法是维护一个"是否真的用户交互过"的 ref，只有用户触发 onChange 才把它置 true；发 PUT 前还要拿即将写的值跟"当前已知的真相"做一次内容比对，双保险防止"内容没变但 updated_at 变了"这种伪写。⑥项落地时应该直接复用这一套机制，不是从零设计防线，并且照抄它的测试模式再补一份"零交互不写"的单测锁住 activity_list_preference。这条更正是为了不让下一轮又把这个坑当成"悬而未决"重新提一遍。

加载策略

  1. 组件挂载：先读 localStorage 缓存，有就立刻渲染（避免云端请求还没回来时界面空等）
  2. 并行发一次 GET 到云端偏好接口
  3. 云端值回来后跟本机缓存比对 updatedAt，谁的时间戳新就用谁校正界面（不是无脑覆盖成云端值）
  4. 校正后的值同时写回 localStorage，保持下次秒显示还是最新的

记住的筛选值失效了怎么办

比如之前筛的支付方式后来被删掉了——渲染时直接过滤掉这个失效值，自动退回「全部」，不弹出提示解释、也不会筛出一个空列表卡住用户，静默处理。

网络请求失败

GET 偏好接口失败（离线/超时）不能卡住或阻塞列表显示，静默退回本机缓存值，列表照常渲染。

需要 Remy 确认（跟⑤项手动拖拽排序有交互冲突，这条要跟左边「⑤ 手动排序可拖拽」那屏一起看）：手动排序模式下，如果同时开着筛选（比如只看"现金"这个支付方式），拖拽调整顺序该怎么处理？
方案 A：允许拖拽，但只在筛选后的可见子集内重新排列——子集内部顺序变了，被筛掉的那些记录顺序原地不动，清除筛选后子集的新顺序"嵌回"原本的位置。灵活，但用户看不到全貌，容易搞混"这几笔的相对顺序"和"全部记录的相对顺序"到底改了什么。
方案 B：筛选生效时直接禁用拖拽手柄（手柄置灰/隐藏），配一句提示"筛选中无法调整顺序，先清除筛选"。逻辑最干净，不会有"看不全还在挪"的困惑，但要求用户多一步操作。
